# Noridoc: Worker

Path: @/src/worker

### Overview

- Runs the authoritative simulation off the browser main thread and defines its message boundary.
- Sends map geometry as needed and pooled, transferable render snapshots when simulation ticks advance or paused commands change state.
- Lets the main-thread UI and renderer consume snapshots and statistics without reading worker-owned simulation objects.

### How it fits into the larger codebase

- [SimClient](sim-client.ts) starts [sim.worker.ts](sim.worker.ts), sends commands and scheduler controls, and receives map data, snapshots, and statistics.
- [SimRunner](sim-runner.ts) owns the [Simulation](../sim/core/simulation.ts) and advances it through [FixedStepScheduler](scheduler.ts). Its pump applies due ticks, updates timing statistics, and publishes snapshots when a pooled buffer is available. When paused, construction commands and `setPersonPosition` are applied immediately without scheduler advancement and changed state is published on the next pump; other commands are held and enqueued when the game resumes. Moving a person therefore updates the authoritative world and snapshot while leaving the tick and simulation systems untouched.
- [snapshot.ts](snapshot.ts) translates simulation columns into render and UI data for [src/render](../render/docs.md) and [src/ui](../ui/docs.md). Each published snapshot has a monotonically increasing `revision` independent of its simulation `tick`, so consumers can detect paused-state publications even when the tick and pooled buffer identity repeat. Along with buildability, it publishes per-tile ground care, stable staff IDs and patrol allocation IDs aligned with the staff render layer, packed 4×4-block patrol masks, staff names keyed by ID, guest details aligned with the guest layer, ride information for the UI and ride markers, track operating modes, and successful build/demolish audio cues.
- `Snapshot.staffStats` carries `STAFF_STAT_STRIDE` (9) values per worker: litter swept, lawns mown, gardens watered, bins emptied, rides inspected, rides fixed, vandals stopped, guests entertained and the hire tick. The worker window reads them by role.
- Snapshots also carry the current derived occupancy volumes for the track builder ghost. `SimRunner` reconstructs that list from the world on each snapshot; preview validation uses it to show collisions before a build command reaches the simulation. Loading scans the rebuilt world for overlapping ride-related elements and returns names as warnings in the `loaded` reply; `SimClient.loadWarnings` exposes them to the save/load UI.
- The browser's [audio engine](../audio/docs.md) consumes these snapshot cues and ride/weather state on the main thread. Sound playback is an observer of snapshots and does not send commands to or gate the simulation.
- `setSnapshotInterval` (sent by the main thread from its measured frame time) sets a minimum spacing between published snapshots; ticks still run at the fixed rate and stats are unaffected.
- Snapshot buffers travel as transferable `ArrayBuffer`s. The client returns consumed buffers to the worker for reuse, keeping the simulation thread as the sole owner of live world state.

### Core Implementation

- [protocol.ts](protocol.ts) defines initialization, simulation command, speed, pause, recycle, save, load, map, snapshot, stats, and reply messages. `previewPaths` asks what each footpath placement would become if the run were laid now; the reply, `pathPreview`, carries one piece description per placement (result, base level, slope, queue flag, style, final joined-edge mask, and queue-line status bits for a ride entrance and an open end connected to ordinary path). The edge mask supplies the connected directions used to preview rails. It is answered by request id, so it does not share the save/load queue. `init` may carry a scenario definition, which the worker applies with `prepareScenario` before the first tick. Map messages include the gate tile coordinates alongside map geometry and path records; bootstrap uses that entrance context for the opening camera. `save` replies with the game's bytes (`saved`). `load` replaces the running game with a save (`loaded`) or fails with `error`.
- [SimClient](sim-client.ts) exposes `startGame`, `save()` and `load(bytes)` as promises. Replies to a save or load are matched to the oldest request of that kind. Snapshots that arrive between a start or load request and its confirmation belong to the previous game, so the client recycles and drops them.
- A snapshot layer has a count and four `Int32` values per entity. For guests, staff, vehicles, and litter, the values are fixed-point x, y, z, then packed state and tint or kind. Guest rows pack tint in bits 0-7, facing in bits 8-9, last heading in bits 16-23 and the guest's `GuestState` in bits 24-31; bit 10 marks a standing-still guest and bit 11 a guest actually on its bench seat (`guestRowSeated`, set only in `Sitting` once the guest has reached the seat, not while it walks to or rises from it); a sitting guest's heading is the direction it faces. Read them with `guestRowHeading` / `guestRowState` / `guestRowSeated` rather than shifting by hand. `staffIds` aligns stable IDs to staff rows, while `staffNames` maps those IDs to player-given names. Ride, track and car layers use their fourth value for renderer metadata.
- `SimRunner` assigns the next monotonic snapshot `revision` immediately before every snapshot publication. It does not derive this value from `tick`: paused commands can publish changed world state without advancing simulation time, and snapshots reuse pooled buffers. Renderer pick-target caches key off this publication revision alongside camera, viewport and atlas state, not tick or typed-array identity.
- Ride entries are positioned at their entrances and carry the stable ride ID in the fourth value. Track entries carry tile-centered position and height (fixed-point x and y at 256 per tile; z already in world units, the piece's track-step height times `TRACK_Z_STEP`); their fourth value packs ride ID in the high 16 bits, a 3-bit piece drive mode (chain lift, brake, block brake, ...) in bits 10-12, direction in bits 8-9, and piece type in the low 8 bits. The vehicles layer's fourth value likewise carries the ride ID in its high half, which the renderers use to skip marker drawing for rides drawn with sprites.
- [car-poses.ts](car-poses.ts) fills the `cars` layer: one row per car of every train, with x, y, z and a packed pose word (ride ID in the high half, then passenger count, bank class, pitch class and eighth-turn heading; `encodeCarPose` / `decodeCarPose`). Each car sits `(index + 0.5) * CAR_LENGTH_Q8` behind the train's track position on the ride's `VehicleTrack` polyline (wrapping on loops, clamped at the start otherwise), interpolated along its segment. Heading is the segment direction rounded to eighths of a turn; pitch is the segment slope bucketed into -3..3 (about 25, 60 and 90 degrees); bank is level, left, right or inverted from the segment's bank sine and cosine and inverted flag. Total train passengers are distributed across its cars, with the remainder assigned to the first cars; the per-car count is capped at seven in the packed pose. [src/render](../render/docs.md) resolves the ride ID to its coaster family, then uses the packed pose to select that car's generated sprite, including the loaded/empty water-boat variant; the pose classes and available sprite variants are defined together by [tools/sprites](../../tools/sprites/docs.md).
- `guestDetails` contains needs, cash, a thought cursor, and the four-entry thought history in guest-layer order. `grounds` is a byte per tile for grass overgrowth and flower-bed state. Patrol allocation IDs align with stable staff IDs and the staff render rows; each ID addresses a row of packed 4×4-tile blocks in `patrolAreas`, with `patrolWordsPerArea` giving the row width. The snapshot also includes weather, a park summary, and scenario state. Static map dimensions, gate coordinates, heights, surface classes, slopes, water levels, ownership flags, and map elements travel in a separate map message. Ownership flags let renderers distinguish owned land, unowned land, and land or rights offered for sale. Path records include connection flags, addition/bin data, and persisted surface style; scenery records carry tile, height, rotation, and catalog item. Periodic statistics report tick, guest count, smoothed and peak simulation cost, and dropped ticks.
- `previewLand` requests are answered with a `landPreview` message carrying the `LandPlan` (result, price, changed vertices and tiles) without changing the world; `SimClient.previewLand` keeps only the newest answer. `previewArea` works the same way for the Clear scenery and Water tools: the worker runs `planArea` and answers with `areaPreview` carrying an `AreaPlan`; `SimClient.previewArea` / `clearAreaPreview` track a separate request sequence, and `SimClient.areaPreview` holds only the answer to the newest request together with the edit it answers, so callers compare edits before trusting it.
- `buildable` is a `Uint8Array` indexed by map tile. Each snapshot fills it from the map's `canBuild` result, representing owned land or construction rights for that tile.
- `rideInfo` carries `RIDE_INFO_STRIDE` ints per ride in ride-layer order: stable ID, type/state/phase, ratings, queue length, placement/test flags, guests served, price, track piece count, construction cursor (`CursorX`/`CursorY` tile and `CursorZ` height in track steps, half a land level), entrance/exit tiles, reliability, lifetime income in cents, the ride's footprint anchor tile (`RideX`/`RideY`), its current demolition refund, its orientation in quarter turns (`Dir`) and, for flat rides, the floor height level (`BaseLevel`: the highest ground corner under the footprint), its queue tile count, estimated wait in ticks, line capacity and queue limit, then rolling downtime percent (`Downtime`), the inspection interval in minutes (`InspectionMinutes`, 0 = never), minutes since the last inspection (`MinutesSinceInspection`) and the derived `MechanicStatus` (see the [rides module](../sim/rides/docs.md)). `PhaseProgress` is the permille of the Running phase already elapsed (0 in other phases); renderers spread long ride animation profiles, such as the Swinging Ship pose sequence, across it. `TrainsSet`, `CarsSet`, `MaxTrains`, `MaxCars`, and `Capacity` report the configured train layout, its track/station limits, and the resulting guests per dispatch. `StallFront` is the `RideResult` explaining why guests cannot buy from a stall's or facility's window (`Ok` when they can, and for every other ride), computed with the simulation's own `stallSlotProblem`; for stalls `Dir` is the service-window direction and `EntrancePlaced` means the front serves guests (see [rides](../sim/rides/docs.md#stall-storefronts)). `RideFlag.HasQueue` marks a ride entered through a built queue; `park.orphanQueueTiles` counts queue tiles no ride owns. Guest rows carry an idle bit for standing guests. Refund calculation is shared with the simulation's demolition command through [ride-refund.ts](../sim/rides/ride-refund.ts). Cursor direction, slope, bank, and track presence are packed with `encodeCursor` / `decodeCursor`.
- The ride row also carries kiosk/stall second price and per-item sales counters. Guest metadata bits 11–13 select balloon, hat, and rain-umbrella overlays; the final `guestDetails` word carries the full set of items visible in the guest window.
- `TowerHeight` and `TowerCabinLevel` ride-info values carry Observation Tower height (land levels) and cabin height in thousandths of a level, computed in the worker by `observationTowerCabinMilli` from elapsed ticks, including stranded and returning cabins; renderers and previews read the value rather than recomputing the motion.
- `feedback` copies `world.feedback` (`seq`, `domain`, `code`, `subject`) so the UI can show the outcome of its latest command.
- Successful build and demolition commands append monotonically identified events to the world's transient audio-event queue. Snapshot publication copies and clears that queue; event ids let the audio consumer ignore cues already observed when snapshots are repeated or recycled.

### Things to Know

- Snapshot buffers, including patrol masks, staff patrol IDs, the track-piece layer, and per-tile `buildable` array, are transferred rather than copied. The map message's ownership and terrain arrays are also transferred. After transfer, the sender's typed-array backing buffers are detached until the client returns snapshot buffers in a recycle message; map data is independently re-extracted when the map revision changes.
- Three snapshots are pooled. The pool is sized for the largest map seen so far and grows only when a larger map arrives; recycled buffers smaller than the current pool are dropped. If none is free after simulation ticks advance, publication is skipped so the simulation can continue while the main thread catches up.
- A new game or a load replaces the running `Simulation` in the same worker. The pool and the scheduler's speed and pause state carry over, so the player's settings survive a new game.
- Ride rendering entries expose stable IDs rather than ride state or type. The UI uses these IDs to associate track pieces with a ride; ride type and operating state remain in the simulation state.
- `economy` (price mode, admission price, loan limit, park value, this-month and last-month ledger totals by `LedgerCategory`) and `research` are plain objects in each snapshot. Research data includes funding, enabled categories, progress and work required, the current or next eligible item and its player-facing stage, and unlocked ride flags; the UI uses these fields for the Research window and unlock news.
- The snapshot publishes `wageBillPerWeek` directly from the economy ledger. Staff salary constants retain the manual's monthly amounts, converted to rounded weekly cents when staff are hired. On load, pre-v16 saves rebuild the weekly input from the current staff roster; v16 saves retain the serialized weekly ledger input.
- `rideInfo` is transferred and recycled like the other buffers; `feedback` is a plain object that travels with the snapshot message.
- `audioEvents` is a plain transient array rather than a simulation-state column: it reports purchases and player actions to the browser, while the vehicle system emits drop screams and chain-lift clanks. The browser consumes each snapshot's cue list independently of simulation decisions.
- The `cars` layer is a pooled transferable buffer like the others, sized by default at the vehicle capacity times the maximum cars per train.
- Ride and track layer counts are capped by their output-buffer capacities, while the park summary's ride count reflects the full simulation count. The track layer and `buildable` array follow the same pooled transfer and recycle lifecycle as the other snapshot buffers.
