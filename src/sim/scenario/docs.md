# Noridoc: Scenario Simulation

Path: @/src/sim/scenario

### Overview

- Defines scenario starting finances, pricing, ride and shop availability, research, entrance placement and objective state, plus each scenario's generated map and pre-built rides.
- Validates scenario JSON and evaluates dated or open-ended objectives against the simulation.
- Keeps the active objective, win/loss status and the park rules (optional scenario restrictions) in `World` for deterministic saves and continuation.

### How it fits into the larger codebase

- The worker prepares new scenarios through [prepareScenarioPark](scenario-layout.ts): it applies scenario settings, connects the entrance to an edge spawn point, then materializes ambient trees.
- [scenario-file.ts](scenario-file.ts) validates documents loaded by [catalog.ts](catalog.ts); errors identify the scenario and field, while duplicate IDs invalidate the catalog.
- [scenario-preview.ts](scenario-preview.ts) turns a prepared scenario `World` into a deterministic top-down, one-pixel-per-tile overview. The build-time generator uses the same scenario parser and `prepareScenarioPark` path as a new game (approach path and ambient trees included), so previews reflect each JSON map rather than a shared title-screen illustration.
- [scenario-system.ts](scenario-system.ts) runs after economy processing and reads current guest, ride, track, economy and ledger state when evaluating a deadline.
- [scenario.ts](scenario.ts) owns the flat objective record and terminal status in `World`; [save.ts](../../save/save.ts) preserves those fields without storing the source scenario document. A loaded park keeps the map, ownership and rules stored in its save; loading never regenerates a map from the current scenario JSON, so remixing a scenario file only affects new games.
- The title screen ([title-screen.ts](../../ui/title-screen.ts)) shows the optional root `landscape` and `challenge` strings as Terrain/Challenge lines alongside the restriction rules. The balance harness and hard-park playtests in [bench](../../../bench/docs.md) prepare parks through `prepareScenarioPark`, the same path as a new game.
- In the final world-fidelity balance run, the default seed (2026) wins at park rating 474 against the 450 target after the trash rate was calibrated from one-in-48 to one-in-96. The earlier deferred-economy seed sweep is a separate baseline. See [docs/BALANCE.md](../../../docs/BALANCE.md#world-fidelity-pass) for the comparison and assumptions.

- [scenario-map.ts](scenario-map.ts) generates terrain and land ownership when configured and scatters scenery from a scenario recipe; tree-only recipes can decorate the default map without replacing its seeded terrain. [scenario-shapes.ts](scenario-shapes.ts) holds the shared shape geometry (distance, containment, bounding rect) used by land parcels, terrain shapes, tree stands and clearings. Starter Park configures a flat, owned apron 30 tiles wide by 20 tiles inward from the south entrance (600 tiles) at height 4, with surrounding terrain graded gently toward base height 2 and hills and a lake farther from the entrance. This gives new parks clear building space while keeping terrain features beyond the entrance area. The generator uses seeded placement and keeps scenery clear of the entrance apron and any configured gate-to-park corridor. [scenario-prebuilt.ts](scenario-prebuilt.ts) places standing rides; [park-grid.ts](park-grid.ts) is the gate-relative coordinate frame shared with the balance strategies in [bench/strategy](../../../bench/strategy).
- The shipped catalog is every `scenarios/*.json`, spread across the Beginner, Challenging, Expert, Real and Other tabs. The hard parks (Challenging and Expert) combine parcel land, terrain shapes, tree stands and restrictions to recreate RCT2-style awkward sites; their intent is described in [docs/scenario-remixes.md](../../../docs/scenario-remixes.md). Each tab's scenarios and objectives are listed with their scripted win rates in [docs/BALANCE.md](../../../docs/BALANCE.md#scenario-win-rates). Completion is remembered per browser by [scenario-progress.ts](../../save/scenario-progress.ts) and shown by the title screen.

### Core Implementation

- `generateScenarioMap` replaces the default seeded terrain only when a file has a `terrain` block. Height shaping runs in this order: coarse noise (`relief`, `cell`), `hills` and `lakes` over `baseLevel`; then `terrain.shapes` in order; then the apron is fixed at `buildLevel` with surrounding vertices constrained by distance so the level change returns gradually; then `relaxTerrain` keeps every slope legal. A `raise` shape lifts ground to at least `level` inside the shape, a `lower` shape cuts it to at most `level`, and both fall away one level per `run` tiles outside it, giving ridges, shelves and channels. The apron is `buildLength` tiles inward from the gate edge and `buildWidth` across, flush with the owned edge and centred `apronOffset` tiles along it from the owned land's midpoint. Water fills every tile whose ground is below `seaLevel`, wherever it is, so a lowered shape below sea level floods even inland. Surfaces come from `groundSurface`: ground at or above `terrain.highland.level` takes the highland surface, steep exposed faces become rock, and the rest use `surface`. Tree-only recipes can still scatter scenery on the default map when no terrain recipe is present.
- Shapes are tile-coordinate regions: `rect` `[x0,y0,x1,y1]` (inclusive), `ellipse` `[cx,cy,rx,ry]` around a tile centre, or `band` `[x0,y0,x1,y1,halfWidth]`, a thick line between two tile centres. A tile is inside a shape when its centre is; terrain shapes measure distance from vertices.
- `landOwnership` computes each tile's starting ownership flags. Margin land (no `parcels`): `land.ownedMarginPercent` insets the owned rectangle (default 25, Starter Park's centre half), `land.saleMarginPercent` leaves an outer ring unsellable, and [expansionOwnership](../map/tile-map.ts) marks the immediate ring around owned land `SALE_LAND` and farther tiles `SALE_RIGHTS`, so the renderer and purchase UI can distinguish buying land from buying construction rights. Parcel land: `land.parcels` is an ordered paint list of shapes, each with kind `owned`, `land` (land for sale), `rights` (construction rights for sale) or `none`; later parcels override earlier ones and unpainted tiles are not for sale. Either way the map border is never owned or for sale. `ownedBounds` is the inset rectangle for margin land or the bounding box of owned tiles for parcel land; the gate edge and apron are measured from it. Margin recipes produce the same maps they did before parcels existed. The flags feed map buildability and are refreshed per tile during generation.
- `trees` configures tree and grove counts, with a share of solitary trees, on flat dry owned-or-for-sale ground that suits each species: grass supports the configured tree species, sand supports palm and cactus, and rock takes none. `trees.stands` fill a shape before the scattered trees: each dry, empty, owned-or-for-sale tile in it (slopes included) gets a piece with `density` percent chance, of which `rocks` percent are boulders or rock clusters instead of trees. `trees.clearings` are shapes kept free of generated trees and ground scenery. Optional `shrubs` and `flowerBeds` add ground scenery; `clearWidth` is the half-width and `clearLength` the inward reach of a gate-aligned corridor (following `apronOffset`) reserved in addition to the apron and its two-tile margin. The generator is seeded from the world seed, so terrain and scenery placement are repeatable for a given seed.
- `prepareScenario` applies terrain, places the entrance and standing rides, and applies scenario state. The worker calls `prepareScenarioPark`, which then lays the gate-to-map-edge approach and records its spawn point before materializing seeded ambient tree copses, passing `treeClearAreas` (the configured build apron plus the bounding rect of each `trees.clearings` shape) as clear areas. A standing ride's `row`/`lateral` name its front corner (the footprint tile nearest the gate and the spine) and the footprint extends away from both, oriented to reach least across the spine (`rideFrontage` in [park-grid.ts](park-grid.ts)). Construction of standing rides is free because cash and the month's ledger are reset afterwards. Standing rides use `prebuilt` entries (`type`, `row` inward from the gate, signed `lateral` across the spine of at least 2) and are opened with a queue, entrance and exit.
- [ambient-trees.ts](../map/ambient-trees.ts) runs after scenario content and its approach are placed, and after default sandbox initialization has established its approach. Its seeded value-noise fields form clustered forests and group species by cluster, while map edges and the unowned side of ownership boundaries carry denser tree belts. Owned interiors have only sparse ambient trees, and the gate approach stays open. Scenario initialization excludes the full configured build apron, the recipe's clearings (as bounding rects) and the entrance radius, preserving the flat build zone. These ambient candidates supplement scenario recipes, whose explicit tree and grove counts remain separately configured in [scenario-map.ts](scenario-map.ts). Existing occupancy prevents trees from being placed on paths, water, rides, track, entrances, or other scenery. Trees are stored as ordinary `SmallScenery`, so the shared map occupancy checks block construction through them and Clear scenery can remove them. Older saves use a separate migration path that reconstructs the former renderer's coordinate and species pattern on unoccupied tiles.
- Scenario preview pixels start from terrain surface colours shaded by tile height, then apply water or ownership tints. Entrance, paths and queue paths, ride footprints or track, and scenery are drawn as tile markers above that base. Preview generation writes native-size and nearest-neighbour 2× PNGs plus source hashes; see [scenario preview generation](../../../tools/scenario-previews/docs.md).

- [scenario.ts](scenario.ts) defines objective kinds and the numeric objective record, and applies starting finance, price policy, research availability and objective state. Each scenario's `availableItemIds` selects its starting attractions and services, while its invention list supplies later research; the scenario set is authored to give parks several gentle rides, essential services and at least one coaster or thrill ride from the start. Open Grounds makes the entire ride catalog available and has no research queue. Scenario-specific maps, objectives and starting cash remain defined in the scenario documents. [scenario-layout.ts](scenario-layout.ts) also places and registers an optional gate path.
- [scenario-file.ts](scenario-file.ts) validates bounded numeric fields, enums (including optional climate), income category masks, optional coaster thresholds and deadlines. Each shape must set exactly one of `rect`, `ellipse` or `band` with in-map coordinates, and a zero-`halfWidth` band must run along a row or column. Parcel land must own at least one tile, the owned tiles must form one 4-connected piece, and `land.parcels` requires a `terrain` recipe (only terrain generation paints ownership). Every build-apron tile must be owned; the error names the apron rect and the first unowned tile. It converts `byYear` to simulation ticks; a `byTick` deadline is used as supplied. Scenario JSON does not need to match an embedded interface shape beyond the fields the parser accepts.
- [restrictions.ts](restrictions.ts) owns `ScenarioRestrictions` (no tree removal, no landscaping, a construction height cap, banned ride types, no marketing), its parser, the predicates the enforcing modules call, and the player-facing rule and refusal strings. `parseScenarioFile` also rejects a banned ride type that appears in `research.availableItemIds`, `research.inventions` or `prebuilt`. `applyScenario` copies the rules into `world.scenario.restrictions` after standing rides are placed, so prebuilt rides are never subject to them; sandbox and imported parks keep an empty object. Enforcement lives in the owning command modules ([map](../map/docs.md), [track](../track/docs.md), [rides](../rides/docs.md), [economy](../economy/docs.md)), each returning its own refusal code. The contract is [docs/scenario-restrictions.md](../../../docs/scenario-restrictions.md).
- Scenario climate is applied to the world weather state, hashed and saved; scenarios that omit it use the warm default. The starter scenario declares that default explicitly.
- [scenario-system.ts](scenario-system.ts) judges dated objectives once, on the first tick at or after their deadline; the result is terminal. Families include guest count/rating, park value, loan repayment plus park value, monthly income, ride counts, qualifying or complete coasters, best-ride excitement and `HaveFun`. Aliases include `guestsByDate`, `parkValueByDate`, `monthlyRideIncome` and `monthlyFoodProfit`.
- `monthlyFoodProfit` uses net food/drink sales and stock costs. Kiosk and toilet revenue is recorded as general shop sales and does not satisfy that objective.
- Ride objectives scan ride and track stores at the evaluation tick. `QualifyingRides` counts open non-shop attractions; `BuildRides` counts current ride entities; `QualifyingCoasters` counts distinct open track-ride types meeting excitement and length thresholds; `CompleteCoasters` counts rides with a closed track and sufficient excitement; `BestRide` compares excitement for open rides. These criteria describe current state, not lifetime achievements.
- `MonthlyIncome` reads the most recently completed month. `Guests` may require a minimum park rating; `GuestsAndRating` requires both guest and rating thresholds; `RepayLoanAndParkValue` also requires zero loan. Park-value objectives use the economy's latest published park value input. `HaveFun` has no deadline and remains active.
- The [objective UI](../../ui/objective.ts) reads the objective and live metric. The park window shows the objective, active awards and current date; the HUD shows objective status and announces recent award news.

### Things to Know

- Park value includes the economy's valuation of closed non-shop rides and current guest count, but its ride inputs refresh periodically; an objective can therefore observe the most recently published value at its evaluation tick.
- Coaster length uses the track system's stored centre-line tile length. Objective field semantics and thresholds remain compatibility assumptions where checked-in mechanics sources do not establish original RCT2 behavior; see [docs/DECISIONS.md](../../../docs/DECISIONS.md).
- The height cap is measured per tile from local ground (lowest land corner, or the water surface when higher), not from the map base. `aboveHeightCap` takes plain height arrays so client previews can run the same check against snapshot map data.
- Restrictions only gate new actions; nothing already standing is removed when they apply. `hashWorld` mixes them only when a rule is set, so unrestricted worlds keep their old hashes.
- Entrance search starts at the owned-bounds edge midpoint shifted by `terrain.apronOffset` and takes the first straight inward run of the requested length that is buildable, flat, dry and empty. If no run qualifies, no path or gate is placed.
- Because `ownedBounds` for parcel land is a bounding box, its edges can cross unowned tiles; the parser's apron-ownership check is what guarantees the gate area is actually owned.
