# Noridoc: Rides

Path: @/src/sim/rides

### Overview

- Defines ride types and owns per-ride state, operating cycles, ratings, reliability, maintenance, and ride commands.
- Covers flat rides, service stalls and facilities, transport rides, coasters, and tracked water rides such as Log Flume and River Rapids.
- Ride state uses deterministic integer data and is part of the simulation's saved and hashed world state.

### How it fits into the larger codebase

- Ride instances live in `World.rides`, a struct-of-arrays `EntityStore` defined by [ride-store.ts](ride-store.ts) and created by [core/world.ts](../core/world.ts). The core state hash includes this store through [core/hash.ts](../core/hash.ts). [save/save.ts](../../save/save.ts) writes ride columns in save version 4 and migrates version 3 rides by replacing only the legacy ride schema segment, preserving allocator IDs and surrounding track arrays. Migrated rides remain closed until entrance/exit placement and queue connection are configured.
- [ride-system.ts](ride-system.ts) runs in the ordered simulation tick through [core/simulation.ts](../core/simulation.ts). It advances ride phases and age, then runs the time-based reliability and breakdown checks of [ride-maintenance.ts](ride-maintenance.ts) using the world's seeded PRNG.
- Ride-associated ticket, stall, food/drink, toilet, and kiosk receipts accumulate in the ride's lifetime `incomeCents` field; [save/save.ts](../../save/save.ts) persists it from version 8 and defaults older versions to zero. Version 11 appends `reliabilityRaw`, `mode`, `breakdownReason`, `serviceTicks` and `serviceLastTick`; version 12 appends the rolling rider-history columns after them. Older saves initialize absent fields from the legacy reliability percent/default mode and zero rider history.
- Placement accepts tile coordinates from callers and checks them against [map/tile-map.ts](../map/tile-map.ts). Queue lines are derived by [queue-lines.ts](queue-lines.ts) (see below); [core/simulation.ts](../core/simulation.ts) refreshes that derived state after path placement, path-run placement, or removal. [Guest behavior](../guests/docs.md) walks guests to the entrance over the footpath network (queue tiles are ordinary path elements with the queue flag, accepted as `Surface.Path` or `Surface.Queue`).
- The track workstream owns layouts ([track](../track/docs.md)) and [vehicles](../vehicles/docs.md) own train physics and test-run metrics. [coaster-system.ts](coaster-system.ts) (ordered right after `vehicles` in `SYSTEM_ORDER`) bridges them for rides whose type has `usesTrack`, including Log Flume and River Rapids; [ride-system.ts](../ride-system.ts) skips those rides. Water rides use the same test, queue, train dispatch, and measured-rating path as coasters, with water-specific vehicle controls described in [vehicles](../vehicles/docs.md); [ride-operations.ts](../ride-operations.ts) exposes the validated measured-stat interface.
- Ride setup and status commands (`placeRideEntrance`, `placeRideExit`, `setRideStatus` with `open` / `close` / `test`) are routed from [core/simulation.ts](../core/simulation.ts) to [ride-commands.ts](ride-commands.ts). `createRide` and these commands report a `RideResult` ([ride-results.ts](ride-results.ts)) through `world.feedback`; core rejects ride types that are not yet research-unlocked with `ResearchRequired`.
- [staff](../staff/docs.md) owns staff entities and movement. A mechanic walks to a broken ride, or to one whose inspection is due, and calls `serviceRide` every staff update while standing at it; `rideServiceX/Y` give the tile to walk to: the ride's exit once placed (a footprint's own tiles are not walkable), otherwise its own tile (stalls).
- Ride trips record completed riders into rolling ride history in [ride-store.ts](ride-store.ts). [Economy park inputs](../economy/park-inputs.ts) reads that five-minute total and values every non-shop ride, including closed rides, for park value.

### Core Implementation

- [ride-footprint.ts](ride-footprint.ts) owns flat ride geometry. `RIDE_CATALOG[type].footprint` lists the covered tiles at orientation 0 (sizes and sources in [fidelity/rides.md](../../../docs/fidelity/rides.md#flat-ride-footprints)); `rideFootprintTiles` rotates them about the anchor tile (`rideX`/`rideY`) by the ride's `dir` column using `rotateTile`; `validateRidePlacement` checks terrain and then tests the candidate's complete rotated footprint against the shared [occupancy model](../map/docs.md), returning `RideResult.Blocked` for an occupied volume. `rideBaseLevel` is the floor level (highest ground corner). Demolishing a ride frees its tiles because occupancy is derived from live ride columns. [ride-footprint-migration.ts](ride-footprint-migration.ts) gives pre-v20 saves a footprint (see [save](../../save/docs.md)).
- `RideTypeDef.trackClearanceWorld` supplies the clearance used for each track footprint cell owned by that ride. It converts the RCT2 descriptor's `Heights.ClearanceHeight` coordinate units using four project world units per source unit. Current source values are grouped here:

  | RCT2 descriptor clearance | Project world units | Ride types                                                                                        |
  | ------------------------- | ------------------: | ------------------------------------------------------------------------------------------------- |
  | 24                        |                  96 | Looping Roller Coaster, Wooden Roller Coaster, Junior Roller Coaster, Steel Wild Mouse, Log Flume |
  | 32                        |                 128 | River Rapids, Miniature Railway, Monorail, Chairlift                                              |

  These values are sourced from the respective [coaster](https://github.com/OpenRCT2/OpenRCT2/tree/develop/src/openrct2/ride/rtd/coaster), [water ride](https://github.com/OpenRCT2/OpenRCT2/tree/develop/src/openrct2/ride/rtd/water), and [transport ride](https://github.com/OpenRCT2/OpenRCT2/tree/develop/src/openrct2/ride/rtd/transport) descriptors; for example [LoopingRollerCoaster.h](https://github.com/OpenRCT2/OpenRCT2/blob/develop/src/openrct2/ride/rtd/coaster/LoopingRollerCoaster.h) and [RiverRapids.h](https://github.com/OpenRCT2/OpenRCT2/blob/develop/src/openrct2/ride/rtd/water/RiverRapids.h). OpenRCT2 construction reads ride-type clearance together with per-sequence track clearance metadata in [RideConstruction.cpp](https://github.com/OpenRCT2/OpenRCT2/blob/develop/src/openrct2-ui/windows/RideConstruction.cpp) and [TrackData.cpp](https://github.com/OpenRCT2/OpenRCT2/blob/develop/src/openrct2/ride/TrackData.cpp). In this simulation, the track piece's rotated footprint cell `zMin`/`zMax` remains tile-specific; support columns are not separately modelled as occupancy volumes.

- [ride-commands.ts](ride-commands.ts) creates rides, validates and places entrances/exits, opens/closes/tests rides, and demolishes rides. Ordinary rides require boarding points and a connected queue; track rides also require a passed test. Stalls and facilities use a neighboring public path as direct access.
- Entrance and exit candidates are accepted around the complete flat-ride footprint or the footprints of every coaster station piece, then checked as boarding volumes against shared occupancy. Queue and ordinary path tiles may share a base-height tile with ride boarding points; the park entrance can share that path tile and can also coincide at the same base height directly with a ride entrance/exit. A queue is connected when its open end joins an ordinary path (or the entrance itself sits on a path). Path placement and removal refresh this derived state.
- Flat-ride tests run a deterministic dry cycle without guests or replacing authored ratings. Track rides use [coaster.ts](coaster.ts) and [coaster-system.ts](coaster-system.ts) to run vehicles and record measured test statistics; this includes Log Flume and River Rapids, whose water-track rules are defined by their ride types.
- [ride-refund.ts](ride-refund.ts) calculates construction cost from the ride catalog plus its attached track pieces, then returns the full cost if no guest was served or 70 percent rounded down otherwise. The same calculation feeds the ride-window refund preview through [worker snapshots](../../worker/docs.md) and the authoritative demolition command. Demolition aborts testing, removes trains, clears guests' ride targets and navigation, and moves them to a walkable exit, entrance, or nearest walkable tile; orphaned track is removed by [track-system.ts](../track/track-system.ts).
- [ride-maintenance.ts](ride-maintenance.ts) applies seeded reliability and breakdown checks. Ride income, reliability, operating mode, service state, and rolling rider history are persisted by the save system.

### Things to Know

- `allowsWater` is ride-type capability metadata. Track command validation rejects each rotated piece footprint over open water for rides without that capability; Log Flume and River Rapids may place their track over open water.
- Queue and service access are derived from the map. Removing the last adjacent public path clears a stall/facility's access and closes it; ordinary ride queues must reach at least one regular path tile.
- Flat rides and facilities publish one occupancy volume for each tile in the rotated footprint. Their current default clearance is three `Z_STEP`s above the base; track and other elevated elements can pass over them when the half-open vertical intervals leave clearance. Ride-type track clearances use authored RCT2 descriptor values converted to world units as described above; OpenRCT2's construction checks also account for track-sequence metadata.
- Consecutive station pieces are supported, and every station footprint contributes tiles where entrance and exit candidates can be placed. Any track edit invalidates the ride's tested state.
- Track rides dispatch and unload through the coaster system; flat rides use the regular ride phase system. A ride's phase and guest occupancy constrain when boarding points and operating settings can change.

### Queue lines

- [queue-lines.ts](queue-lines.ts) keeps `World.queues` (derived, not saved or hashed): for every queue tile its owning ride slot and step distance from the ride entrance, and per ride the open-end tile, the ordinary path tile it joins, the queue tile count, and whether the entrance is on a queue at all. It also writes the entrance/exit marks into the map (see [map](../map/docs.md)). `refreshQueueIndex` runs at the start of every guests update and after ride commands; it rebuilds only when the marks or `pathVersion` change. A queue line belongs to the ride whose entrance it connects to by flood fill from that entrance; queue tiles reachable from no entrance are counted as orphans for the ride window warning. A ride whose entrance is an ordinary path tile (old saves, stalls) keeps the previous direct-entrance behaviour.
- Line capacity (`rideQueueCapacity`): four guests per queue tile (`QUEUE_GUESTS_PER_TILE`), entrance tile included, or the operator's queue length limit (`setRideQueueLimit`, ride column `queueLimit`, 0 = none) when lower. `estimatedWaitTicks` divides the whole line (queuing plus waiting guests) into ride trips.
- Line geometry: the line is the polyline through the queue tile centres from the open end to the entrance, continued one tile past the open end through the joining path tile. `queueLineCoord` gives a position's distance along it from the entrance centre (`QUEUE_SPACING` = 64 units, four to a tile); `queueLinePoint` steps a guest down it, so corners and ramps follow the chain. `rebuild` stores each tile's `down` (toward the entrance) and `up` (toward the open end) direction. `updateQueueLines` runs at the start of every guests update, orders every line's `Queuing` and `Waiting` guests by that coordinate and records per guest the coordinate of the guest ahead and its rank (`lineAhead`, `lineRank`), and per ride the last guest (`tail`); `queueEntryBlocked` holds back a joiner while the last guest is within one spacing of the join point. All of it is derived and neither saved nor hashed.
- Boarding takes waiting guests in queue order: each guest's `queueSeq` is the ride's `queueSerial` counter when it joined the line, and `seatQueuedGuests` picks the lowest sequence first.
