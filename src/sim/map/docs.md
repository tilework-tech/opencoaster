# Noridoc: Simulation Map

Path: @/src/sim/map

### Overview

- Owns the deterministic tile map: terrain, water, ownership, walkable paths, and stacked map elements.
- Validates map edits and applies their economy charges through the map command boundary. Player-facing area tools (Land, Clear scenery, Water) each have a pure planner that the worker also uses for previews, so a preview and its command share one set of rules.
- Stores path surface style and scenery as map-element state, alongside bin, bench, rain shelter, and lamp additions on path elements.

### How it fits into the larger codebase

- [World](../core/world.ts) owns `TileMap`; [Simulation](../core/simulation.ts) applies [map commands](map-commands.ts) before the ordered simulation systems run.
- [Pathfinding](../pathfinding/docs.md) and guest/staff systems query walkability and connected path edges. Guests add trash/vomit using the map's path and bin queries; handymen locate and empty filled bins.
- Map arrays feed [world hashing](../core/hash.ts) and [save serialization](../../save/save.ts). `revision` is runtime metadata used by [worker map snapshots](../../worker/map-data.ts) and staff's cached bin index, so it is not persisted.
- [Ambient tree materialization](ambient-trees.ts) runs after the scenario entrance approach is connected to its edge spawn point, or after the default sandbox's gate and edge approach are built. It creates deterministic, seed-driven copses as ordinary small-scenery map elements, so trees participate in the same construction, clearance, save, and Clear scenery rules as placed scenery.
- The [UI](../../ui/docs.md) sends path style, queue-path, scenery, and path-addition placement as commands. Flower beds can also be represented in `World.grounds` for grass care; placeable flower-bed scenery is a separate map element.

### Core Implementation

- [tile-map.ts](tile-map.ts) stores shared terrain corner heights and derived tile heights/slopes, ownership and surface arrays, plus a fixed-capacity pool of stacked elements linked per tile. Ownership starts clear; `canBuild` accepts tiles marked as owned or with construction rights. `expansionOwnership` assigns the land-sale flag to the immediate ring outside an owned rectangle and construction-rights-only flags farther out; both the default terrain generator and scenario terrain generation use this helper after marking the outer map border unavailable. `arrays()` supplies persistent arrays to hashing and save code.
- [land-tool.ts](land-tool.ts) is the player-facing terrain planner. A `LandEdit` (raise, lower, flatten, smooth; a square of tiles; a corner mask for a single tile; an anchor tile for flatten) is evaluated against the whole `World`: owned tiles of the selection are edited (a selection with none is `NotOwned`), changed vertices give the affected tiles and price, and structures that the edit would raise terrain into are rejected. It combines `structureConflict` with shared occupancy interval checks for the proposed terrain rise; small scenery on changed tiles is removed and its removal price added, while a ground-level footpath is re-seated on flat or ramp ground and otherwise refuses. `planLand` leaves the world untouched and feeds the worker's `previewLand` reply; `applyLand` commits. Refusals reach the UI through `FeedbackDomain.Land`. `ownedSelection` and `structureConflict` are also reused by [area-tools.ts](area-tools.ts). Under [scenario restrictions](../scenario/restrictions.ts), every edit is `LandscapingForbidden` when landscaping is banned, and an edit that would remove a tree is `TreesProtected` when trees are protected.
- [area-tools.ts](area-tools.ts) plans and applies the Clear scenery and Water tools. An `AreaEdit` is a square plus `tool: 'clear'` or `tool: 'water'` with a `lower` flag; `planArea` evaluates it without touching the world (the worker's `previewArea` reply) and `applyArea` commits, both returning an `AreaPlan` (result, refusal subject tile, price, owned selected tiles, changed tiles, target water level, removed-item count). It reuses `ownedSelection` and `structureConflict` from [land-tool.ts](land-tool.ts), so the square, ownership and structure rules match the Land tool and result codes are shared `LandResult` values.
  - Clear acts on owned tiles only; construction-rights-only and unowned tiles in the square are skipped, and a square with no owned tile is `NotOwned`. It removes every small-scenery element (each priced at its catalog `removalPriceCents`) and strips bin, bench, shelter and lamp flags (and the addition payload) from paths for free. Nothing to remove is `NoChange`; a total above cash is `InsufficientFunds`. No item refunds money. With the scenario's `forbidTreeRemoval`, Clear leaves trees standing and a square whose only removable items are trees is `TreesProtected`.
  - Water keeps every connected body one flat sheet. `raiseStep` takes the selection's surface (its highest water, or its lowest ground when dry), adds one step, and floods outward over every neighbouring tile whose ground lies below the new surface, so water is bounded by banks and never stands above dry ground; it stops with `WaterSpills` when the body would exceed `MAX_WATER_BODY_TILES` (open ground below the surface), `NotOwned` when it reaches land the park does not own, and `WaterLevelClash` when it meets a lake whose surface is higher. `lowerStep` drops the whole connected sheet at the selection's highest surface by one step; tiles whose ground is at or above the new surface are stored dry (`0`). Each changed tile, including flooded tiles outside the selection, costs `WATER_TILE_ACTION_COST_CENTS`, and `AreaPlan.tiles`/`level` describe the resulting surface for the preview. Other refusals: `TooHigh` above `MAX_HEIGHT`, `TooLow` with no water, `RideInTheWay` / `EntranceInTheWay` from `structureConflict`, and `PathInTheWay` / `ObjectInTheWay` for any element a flooded tile carries below the new level (checked on the selection first so the refusal names what the player pointed at). `flattenWaterBodies` brings legacy stepped water to its lowest sheet level on load. With `forbidLandscaping` the Water tool is `LandscapingForbidden`.
- [land.ts](land.ts) implements terrain, water, and ownership operations. `editTerrain` applies raw vertex moves for the land tool; rectangle raises select the lowest tiles and lowers select the highest; an edit plan simulates the operation, measures all actual vertex-height changes after neighbor propagation, and derives the affected tiles. Terrain edits preserve the one-level neighbor slope invariant and roll back when an element would be buried or invalidly tilted. The map-command boundary prices the changed height units and removes litter from every affected tile.
- [paths.ts](paths.ts) places/removes flat or one-level ramp path elements. `planPathPlacement` runs the checks without changing the map and returns a `PathPlan`; `placePathOutcome` applies it, so the UI preview and the placement share one set of rules. `previewPathRun` applies a batch in order to `TileMap.clone()` and reports each piece's final state; the `placePathRun` command applies the same batch to the live map, so a laid run matches its preview. A placement without an explicit slope follows the terrain: flat ground gets a flat piece, a one-level slope gets a ramp facing its rise, and any other shape is refused as `UnevenGround`. `placePathOutcome` returns a `PathResult` naming the refusal; `placePath` is its boolean form. It recomputes edge connectivity, and attaches one of `Bin`, `Bench`, `Shelter`, or `Lamp` flags to the lowest path selected by the path query. Bin fill is stored as one count on that path element; the four-corner bin occupancy model is deferred. Trash deposited in a bin accumulates up to its capacity, and a handyman empties it.
- `TileMap` exposes the walkable graph per path element: `nodeCount`, `edgeMask(node)`, `step(node, dir)` and `walkNode(tile, z)` number a node `layer * tiles + tile` for up to `WALK_LAYERS` stacked paths per tile, so a bridge and the path under it never connect. `adjoiningPath` finds the neighbouring element whose edge height meets an element's edge (`pathEdgeHeight`, built on the pure `pathEdgeLevel`, which [stall storefronts](../rides/docs.md#stall-storefronts) also apply to snapshot path data); `heightNear` gives a walker the surface of the path nearest its height.
- Path elements persist a surface style (tarmac, crazy paving, dirt) in `TileMap.pathStyle`; queue paths use a path flag and stay distinct from style.
- [scenery.ts](scenery.ts) defines placeable trees, shrubs, gardens, rocks, fountains and statues, themed decorations, and wall scenery (hedges and fences). The catalog is append-only because saves store the item index: indices 0-12 are the original items and 13-31 are the model-generated decorations (sunflower patch, lavender rows, rose arch, flower urn, planter box, boulder, rock cluster, fallen log, tree stump, reed clump, tiered fountain, jet fountain, garden statue, obelisk, sundial, park signboard, flagpole, scarecrow, wishing well), so the expansion needed no save migration. Each definition carries a menu `blurb` and `SCENERY_GROUPS` orders the browse groups; `native` items are drawn from their own four-view model at native size and `directional` items turn with their placement rotation (`elFlags`). Decorations are scenery only: they have no guest, staff or research effect beyond the existing scenery-count rating radius, are never gated behind research or scenario availability, and their clearance height is the model height in 16px levels; checks bounds, ownership/build rights, dry land, and element clearances; and stores the item and placement orientation in a small-scenery element. Wall orientation is one of four tile edges stored in `elFlags`; distinct edges may coexist on a tile, while a second wall on the same edge is blocked. Walls may share a tile with a path and do not reserve the tile centre. `TileMap` advances `pathVersion` when path or wall elements are inserted or removed, invalidating its cached `edgeMask` and the pathfinder's derived graph data. `placeScenery`/`removeScenery` commands charge the landscaping ledger with project-tuned (not original) prices.
- [ambient-trees.ts](ambient-trees.ts) uses seeded, smoothly interpolated value noise at coarse and detail scales to form tree clusters, with a separate broad noise field grouping species within each copse. Density thresholds favor dense strips along map edges and outside owned-land boundaries, sparse trees inside owned buildable land, and a clear radius around the entrance. Scenario initialization also passes the configured build apron as a clear area, keeping the full flat building zone free of ambient trees. Only grass and sand candidates are considered; water and other surfaces are skipped. It gathers occupied tiles from [occupancy.ts](occupancy.ts) after the gate-to-edge approach exists, so paths, rides, track, entrances and scenery are not covered. The save migration uses the former renderer's exact coordinate and species selector on eligible empty tiles instead, preserving the appearance expected by old saves. Once placed, ambient trees are ordinary small scenery to map commands; Clear removes them using the regular scenery removal and pricing rules.
- [occupancy.ts](occupancy.ts) builds a shared, derived view of placed construction as tile volumes with world-unit base and top-exclusive clearance heights. It combines map elements, rotated track-piece footprint cells, full rotated ride footprints, ride boarding tiles (none for stalls and facilities, whose access tile is the ordinary footpath in front, so several stalls may share one path tile), and the park gate; [occupancy-constants.ts](occupancy-constants.ts) holds the current project-tuned clearances. The model is rebuilt from authoritative world state rather than persisted as a second index. Track and ride placement therefore see materialized trees as scenery occupancy, while the save migration uses the same occupied-tile view to avoid inserting trees beneath legacy construction.
- [map-commands.ts](map-commands.ts) validates affordability and ownership for terrain commands, validates affordability for land, water, and path edits, records charges in the ledger, and routes path-addition commands. Path placement and scenery preview/commit test their candidate volumes against the shared occupancy view; when a path volume is blocked, command feedback carries the occupying element's display name so the path tool can report a specific refusal such as “Blocked by Merry-Go-Round 1.” Land edits and absolute `setTileHeight` reject a proposed terrain rise that intersects existing volumes. Ownership distinguishes owned land, construction rights, and land or rights offered for sale; buying a rectangle acquires only matching sale tiles. The `raiseWater` / `lowerWater` / `clearScenery` commands run `applyArea` and charge `costCents` to the landscaping ledger on success; refusals are reported through `FeedbackDomain.Water` or `FeedbackDomain.Clear` (with `LandResult` codes). The older absolute `setWater` command, which sets a rectangle to a given level, remains. When the scenario forbids landscaping, a single guard refuses every land and water command (including `setTileHeight` and `paintLand`) with `LandscapingForbidden` before any other check; with trees protected, single-item `removeScenery` skips trees and reports `TreesProtected` under `FeedbackDomain.Clear`. Path placement (`PathResult.HeightLimit`, judged at the high end of a ramp) and non-tree scenery (`SceneryResult.HeightLimit`) also check the scenario height cap, in both preview and commit; the cap is sent as feedback detail. Prices are named fixed constants at present: terrain changes cost 500 cents per changed height unit, water changes cost 250 cents per changed tile (for both `setWater` and Water tool steps), land costs 10,000 cents per tile and construction rights 4,000 cents per tile. Land purchase controls live in [the UI](../../ui/docs.md); scenario-configured land prices remain unimplemented. Path additions currently have no separate charge. A footpath removal credits `PATH_REFUND_CENTS`, equal to the placement cost. `previewPathPlacement` reports the outcome a placement would get, including the cash check, without changing the map. `previewScenery` uses the same placement rules that `placeScenery` applies, so a scenery ghost and its placement agree. The `placeScenery` command stores the placement orientation in `elFlags`; for wall scenery the value identifies the tile edge, while other scenery retains its item-facing rotation.
- `surface` is a derived draw class; path elements remain the source of path connectivity and height. `occupancyConflict` compares half-open height intervals on the same tile, with edge-mask comparison for two edge-bound objects. Ordinary same-level path crossings, path or queue sharing a base-height tile with ride boarding points or the park entrance, the park entrance sharing a base-height tile directly with a ride entrance/exit, and path/wall coexistence are explicit exceptions; queues do not receive the ordinary path/track crossing exception. Elevated construction can share a tile when the vertical intervals do not overlap.
- Track clearance is ride-type-specific: the placing ride's descriptor supplies its vertical interval, and each track footprint cell supplies its own base and top extent. Flat rides/facilities currently default to three `Z_STEP`s; ride entrance/exit tiles use one `Z_STEP`, and the park gate uses two. These project values are distinct from OpenRCT2's metadata model, which stores element base/clearance and combines ride-type and track-sequence data during construction. See [TileElementBase](https://github.com/OpenRCT2/OpenRCT2/blob/develop/src/openrct2/world/tile_element/TileElementBase.h), [RideConstruction.cpp](https://github.com/OpenRCT2/OpenRCT2/blob/develop/src/openrct2-ui/windows/RideConstruction.cpp), [track metadata](https://github.com/OpenRCT2/OpenRCT2/blob/develop/src/openrct2/ride/TrackData.cpp), [path metadata](https://github.com/OpenRCT2/OpenRCT2/blob/develop/src/openrct2/world/tile_element/PathElement.h), [small scenery metadata](https://github.com/OpenRCT2/OpenRCT2/blob/develop/src/openrct2/object/SmallSceneryEntry.h), and [wall metadata](https://github.com/OpenRCT2/OpenRCT2/blob/develop/src/openrct2/object/WallSceneryEntry.h). The [OpenRCT2 map reference](https://github.com/openrct2/openrct2/wiki/Maps) describes map height steps in world units; descriptor conversion and representative values are documented in [rides](../rides/docs.md).

### Queue lines

- A queue piece is a path element with `PathFlag.Queue`. Queue lines are single file, as in RCT2: each queue piece stores up to two links (`elData` bits 8-11, `PATH_QUEUE_LINKS`, one bit per direction, always mutual) to the queue pieces before and after it, and a ride entrance takes only one. Pieces that touch but are not linked stay separated by rails, so a block of queue tiles shows as parallel lines or a snake, never a plaza. A queue piece joins an ordinary path only at the line's open end ([paths.ts](paths.ts) `queueOpening`): a piece with at most one link that is not a ride entrance already joined to a line, joining one ordinary neighbour, preferring the one straight on from its link. Joined edges (`PathFlag.Edges`) of a queue piece are its links plus that opening.
- Laying a queue piece links it to the line it extends (`attachQueuePiece`): the drag predecessor (`PathPlacement.linkFrom`, set by `withDragLinks` for `placePathRun` and `previewPathRun`) when it has a free slot, otherwise the adjacent line end with a free slot nearest, along its line, to a ride entrance. The last piece of a drag also links to a line end it reaches, so a drag ending beside a ride entrance joins it. A piece never links to a third neighbour (no junctions) or to its own line (no rings). Removing or replacing a piece drops its links on both sides (`unlinkQueuePiece`), which splits the line cleanly. [queue-link-migration.ts](queue-link-migration.ts) derives links for saves made before version 25, including version 24.
- `elData` bits `PATH_ENTRANCE_MARK` and `PATH_EXIT_MARK` record the path tiles that hold a ride's entrance and exit. The [ride queue sync](../rides/queue-lines.ts) writes them (they are saved with the map); the exit mark stops queues joining the exit tile, and placing a normal piece over an entrance (or a queue piece over an exit) is refused. Because an opening depends on its neighbours, `recomputePathEdges` refreshes tiles two steps away.
- A ride entrance (always a queue piece) and exit are gates with one front edge, stored in `elData` bits 12-14 (`PATH_FRONT_DIR`, `PATH_FRONT_KNOWN`; saved with the map). `boardingAllows` lets `recomputePathEdges`, queue linking and `queueOpening` join a gate only across its front edge, so no connection is drawn or walked on its sides or back. `TileMap.edgeMask` keeps an exit as a one-way node (its front edge out, no ordinary tile leads into it), so pathfinding never routes through an exit and wanderers never step onto it. Commands face the gate away from the ride (`faceBoardingAwayFromRide`); `inferBoardingFronts` ([rides](../rides/boarding-front.ts)) derives a missing front from existing connections, and is the save-version-28 migration for older parks.
- `TileMap.edgeMask` (the pathfinder's view) hides queue tiles from the walking network; `pathEdges` keeps the joined edges the renderer and the queue walk use. `previewPathRun` reports `QueueLink` summary bits per queue piece (whether the line reaches a ride entrance and whether its open end joins a path); each piece's final edge mask carries the connected directions used to preview rails.

### Things to Know

- Stored simulation values are integers and map state is deterministic. Do not write derived tile heights/slopes directly; update terrain through its operations so neighboring tiles stay consistent.
- Tile elements are pool slots, not stable IDs. A path addition modifies flags/data on a particular path element; `setPathAddition` requires an in-bounds buildable tile with a path. Vandalism marks a bench, bin, or lamp broken in a reserved payload bit while retaining its addition and contents; placing the path piece again clears the broken state. Broken bins do not accept litter and are not handyman emptying targets.
- Bins collect trash; guests sit on intact benches (see [guests](../guests/docs.md), "Bench resting"); that code reads the bench flag, path joins, queue/boarding-gate status and broken state from this map and caches its bench lookup against the map revision. Benches, bins, and lamps can be marked broken by guest vandalism. Shelter additions are stored on paths, but no current guest system applies a shelter effect. These behaviors are implemented by [guests](../guests/docs.md) and [staff](../staff/docs.md), not by map storage itself.
- Flower beds and grass care live in `World.grounds` and are handled by the staff grounds system; they are not path additions or part of the map arrays. [scenery-effects.ts](scenery-effects.ts) provides a clipped 10×10 scan of small/large scenery and broken paths for guest surroundings; litter is supplied by the guest system. Fountain/music effects and scenario-configured land prices remain outside this module. See [world mechanics](../../../docs/mechanics/world.md) for researched behavior and project tuning.
